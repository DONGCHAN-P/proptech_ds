# 텔레그램 영상 제작 승인 회신 연결

2026-10-14. 기존 `notify.bot` 단일 수신기에 영상 결정 분기를 연결했다. 별도 getUpdates 수신기를 만들지 않는다. 웹훅도 설정하지 않는다.

## 사용자 확인 단계

1. topic: 다음 영상 주제 제안과 선택
2. script: 대본 전달과 승인
3. budget: 유료 생성 시작 전에 외부 API 예상 비용·상한 승인
4. completed: 완성 영상 전달과 수정 의견
5. pre_upload: 최종 검수 결과·영상 버전·공개 범위 승인

다섯 단계 이외의 되돌릴 수 있는 제작 결정은 에이전트가 한다. 예산 초과, 사실 검증 불가, 권리 불명확 등 중요한 변경은 별도 결정으로 묻는다. 기다리는 시간은 승인으로 간주하지 않는다. 하나의 승인으로 다음 단계까지 승인하지 않는다.

## 메시지 규칙

정상 형식 명령도 실패했다는 사용자 피드백에 따라 `logs/video_decisions.jsonl`에 수신 처리와 Codex 전달의 성공 여부·결정 ID·오류 유형만 기록한다. 명령 본문·수정 의견·키는 기록하지 않는다. 큐 전달 성공 시 별도 확인 답장을 보낸다. 관련 테스트 67개 통과. `/note 결정ID 연결 확인`으로 승인 상태를 바꾸지 않고 실제 사용자 회신 경로를 검사할 수 있다.

2026-10-14 명령 처리 보완: `/approve` 또는 `/revise`만 보내면 자동 처리하지 않고 현재 대기 결정 ID와 사용법을 답한다. 결정 ID를 붙인 명령은 봇 이름 접미사(`@봇이름`), 줄바꿈·여러 공백, 슬래시 없는 명시적 `approve 결정ID`도 처리한다. `revise`에는 수정 내용이 필요하다. 허용 개인 대화·발신자 검증과 종료된 결정 차단은 유지한다. 명령 회귀 테스트 및 관련 기존 테스트 총 66개 통과. 기존 수신 봇 단일 재시작 확인. 실제 사용자 회신→이벤트 저장→Codex 큐 전달→작업 반영은 별도 실제 회신으로 확인해야 한다.

`/approve 결정ID`, `/revise 결정ID 수정내용`, `/reject 결정ID 이유`, `/note 결정ID 의견`으로 회신한다. 승인 요청에 실제 결정 ID와 검토할 산출물 버전을 포함한다. 수정 산출물은 새 결정 ID를 발급한다. 단순 '좋아', 이전 메시지, edited_message는 자동 승인으로 처리하지 않는다.

`notify/video_decisions.py`가 pending/approved/revision_requested/rejected 상태와 만료를 관리하고 `output/video_decisions/inbox`에 원자적으로 회신을 기록한다. 허용 private chat과 발신자 ID가 모두 맞아야 한다. 중복 update_id와 이미 종료된 결정은 차단한다. 회신 텍스트를 셸 명령으로 실행하지 않는다.

## Codex 전달

현재 제작 대화 전환 후 `CODEX_THREAD_ID`와 설정의 스레드가 달라 승인 이벤트는 이전 대화로 큐잉되고 있었다. 현재 활성 스레드 `01a13a00-2b87-7460-b2c7-1ac1332bacf9`로 설정을 교정하고 이전 값은 `previous_codex_thread`에 보존했다. 전달 때마다 설정을 읽으므로 수신 봇 재시작은 필요 없다. 이전에 큐잉된 이벤트의 적용 여부는 inbox의 `application_status`를 먼저 확인해 중복 제작을 피한다. 현재 대본 승인 718066294와 예산 승인 718066295는 적용 완료로 기록했다. 새 스레드로 다음 실제 사용자 회신이 도착하는 전체 과정은 별도 확인이 필요하다.

로컬 CLI `codex queue --thread UUID --message TEXT` 지원을 help로 확인했다. 설정의 지정된 스레드에 파일 경로를 포함한 고정 안내문만 큐잉한다. `config/video_telegram_bridge.json`의 `dispatch_enabled`는 true이며 지정 스레드는 `01a130a8-dc9a-7123-b580-011adfba4edc`다. 고정 테스트 메시지의 실제 queue 호출이 성공했으며 메시지 ID `01a13647-7fc6-7652-8caf-f9b6434a55b7`를 받았다. 수신 봇의 PATH에 codex가 없거나 daemon 연결이 실패하면 inbox가 남고 전달 대기 알림을 보낸다. CLI 큐 등록 성공과 사용자 회신으로 에이전트가 다음 작업을 수행하는 전체 과정은 구분한다.

## 실행과 한계

기존 .venv pythonw 부모·자식 봇을 종료하고 `tools/python311/pythonw.exe notify/bot.py`를 창 없이 단일 실행하도록 전환했다. 기존 getUpdates timeout=50초인데 HTTP timeout=30초였던 문제를 65초로 수정했다. 기존 `proptech_ds 봇`과 `proptech_ds 아침브리핑` 예약 작업은 트리거와 설정을 보존하고 위 Python 직접 스크립트 경로로 갱신했다. PC와 인터넷이 켜져 있어야 한다. Telegram은 미수신 업데이트 보관 기간이 제한되므로 장기 오프라인 운용은 피한다.

오프라인 검증: 허용 발신자, 명령 allowlist, 의견 기록, 중복 방지, 결정별 승인, 종료 후 변경 차단, 수정 메시지 차단 통과. 실제 사용자 회신부터 Codex 큐 전달까지는 아직 미검증이다.

## 근거

## 2026-10-16 일반 대화 양방향 연결 수정

확인한 원인은 인증/스레드 오류가 아니었다. 현재 스레드 ID는 실행 환경과 일치하고 봇도 실행 중이었다. 그러나 `video_decisions.handle_update`는 승인 명령만 받았고 일반 문장은 `bot.handle`의 과거 단지 후보 안내로 빠졌다. Codex 답변을 되돌리는 수신기도 없었다. 또한 기존 루프는 메시지 처리 전에 getUpdates offset을 저장하고 있었다.

`notify/conversation_bridge.py`를 추가하고 기존 `notify.bot` 단일 수신기에 연결했다. 일반 문장·사진·문서·영상 첨부는 본인 private chat와 발신자 ID를 확인한 뒤 `output/telegram_conversation/inbox`에 저장한다. 사용자 문장은 셸 인자로 넣지 않고 고정된 JSON 경로만 `codex queue`로 전달한다. 이미지 파일은 명시적 이미지 입력으로 함께 연결한다. 파일은 Bot API 다운로드 범위에 맞춰 20MiB 이하를 받는다. 수신 offset은 저장/처리 성공 뒤 갱신한다.

답변은 설정에 고정한 현재 대화 JSONL의 **사용자에게 보이는** 진행 안내·최종 답변·질문만 읽어 텔레그램으로 전송한다. 추론·도구 출력·다른 대화는 전송하지 않는다. 최초 연결 시 과거 대화는 재전송하지 않고, cursor/outbox를 보존해 재시작 후 이어간다. 긴 답변은 분할하며 질문 도구와 UI의 같은 질문 메시지는 중복 제거한다. 대화 로그 형식은 공식 고정 API가 아니므로 Codex 업데이트 후 확인이 필요하다. 공식 App Server의 알림 모델을 참고했고 로컬 설치본의 queue help와 실제 결과를 별도 검증했다.

실제 검증: 회귀 테스트79개 통과, 파일 잠금으로 중복 poller 차단 확인, webhook 없음, 실제 휴대폰 메시지 update718066297 ‘연결 확인’ 수신·영구 저장·queue 성공, 진행 답변의 Telegram 실제 전송 receipt 확인. 현재 실행 중인 에이전트가 inbox를 확인해 해당 이벤트를 적용했다. 바쁜 턴 중 큐 접수와 후속 턴의 자동 실행 완료는 구분하며, 후자의 활성화까지 이번 검증에서 독립 관측했다고 주장하지 않는다.

명령: 일반 문장/사진으로 제작 요청, `/status`로 연결·전달 대기 확인, `/help`로 사용법 확인. `/approve 결정ID` 등 다섯 승인 게이트는 그대로 유지한다. 자연어 ‘좋아’는 자동으로 버전·비용·공개 승인을 만들지 않는다. 이전 직접 사용자 권한을 재질문하지 않는 원칙도 유지한다.

PC·인터넷·Codex·수신 봇이 실행 중이어야 한다. 큐 접수는 작업 시작/완료가 아니다. 새 대화로 바꾸면 설정의 thread와 transcript_path를 함께 명시적으로 갱신한다. 확인 기록은 `output/telegram_conversation/verification_report.json`, 상태는 `health.json`, 송신 기록은 `outbox`에 있다. 두 번째 getUpdates 봇이나 무제한 자동 API 실행은 만들지 않았다.

- [Telegram Bot API](https://core.telegram.org/bots/api#getupdates): getUpdates offset와 webhook 배타성.
- [Codex non-interactive mode](https://developers.openai.com/codex/noninteractive): CLI 자동화 방식. 설치된 CLI queue 지원은 로컬 help로 별도 확인.
