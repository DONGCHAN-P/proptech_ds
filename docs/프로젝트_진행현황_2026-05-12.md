# 수도권 부동산 데이터 채널 — 프로젝트 진행 현황
**기준일: 2026-05-12** · 참조 설계서: `Step_1-3_데이터_인프라_설계서.docx` (v1.0)

---

## 1. 프로젝트의 큰 그림

설계서가 잡아둔 최상위 목표는 한 줄로 요약된다.

> **"수도권 아파트 시세를 6종 공공 데이터로 매일 자동 갱신해, Daily / Weekly / Monthly Shorts 영상 콘텐츠의 데이터 토대(Step 1~3)를 만든다."**

Step 1~3은 **데이터 인프라**, Step 4~7은 그 위에서 돌아가는 **콘텐츠 제작 파이프라인**으로 설계되어 있다. 인프라가 안정화되지 않으면 4단계 이후가 임시방편 코드로 무너진다는 것이 설계서의 핵심 전제다.

---

## 2. 설계서가 제시한 초기 목표 (장별 요약)

| 장 | 목표 | 의미 |
|---|---|---|
| **1장** | 6종 데이터 소스 명세 (매매 · 전월세 · 단지정보 · 인구 · 학군 · 상권) | 갱신 주기·표준화 단위가 다른 데이터를 같은 파이프라인에 욱여넣지 않는다 |
| **2장** | 저장소 구조 (raw / staged / master / exports) + SCD Type 2 | 원본 영구 보존, 정제 단계 재현 가능, 과거 시점 값 복원 가능 |
| **3장** | 통합 키 `apt_id` 설계 + `pyeong_bucket` 표준화 | 6종 데이터를 (apt_id, pyeong_bucket, snapshot_date) 복합키로 join |
| **4장** | 자동화 스케줄 (일/주/월/분기/연 분리) | 일별 잡이 멈춰도 월별 잡은 살아있도록 위험도 격리 |
| **5장** | `unified_apt_pyeong_daily` 통합 데이터셋 (≈60컬럼) | 4~7단계가 매번 읽을 단일 진실 공급원 |
| **6장** | 데이터 품질 검증 (sanity 8종 + 정정·해제) | 빈 데이터로 영상 송출되는 사고 방지 |
| **7장** | 운영 루틴 (일 15분 / 주 1시간 / 월 2~3시간) | 사람 검수 지점을 명확히 분리 |

## 3. 현재 진행 현황 — 단계별 체크리스트

### 3-1. Step 1 (수집)

| 데이터 소스 | 설계 목표 | 현재 상태 | 산출물 |
|---|---|---|---|
| **매매 실거래가** (RTMS) | 일별 D+1 수집, 수도권 시군구별 | ✅ **완료 + 히스토리** | `raw/rtms_trade/` 38,498개 XML (2006~2026) |
| **전월세 실거래가** (RTMS) | 일별 D+1 수집 | ❌ **미착수** | `raw/rtms_rent/` 비어있음, `staged/rent/` 비어있음 |
| **단지정보** (K-apt) | 월별 스냅샷, SCD Type 2 | ⚠️ **부분 진행** | `apt_id_map.parquet`은 빌드됨 / SCD 스냅샷은 없음 |
| **지역별 인구** (행안부) | 월별 스냅샷 | ❌ **미착수** | `staged/pop_snapshots/` 비어있음 |
| **학군 정보** (학교알리미) | 학기별 스냅샷 | ⚠️ **대체 수집** | 정식 학기 스냅샷 X, `external_data_collector`로 단지 반경 학교 수집 |
| **상권 정보** (소상공인공단) | 분기별 스냅샷 | ⚠️ **대체 수집** | 정식 분기 스냅샷 X, 외부데이터로 카페·학원 등 단지 반경 집계 |
| 보너스 (설계서 외) | — | ➕ **추가 수집** | `raw/park/`, `raw/subway/` (지하철역 거리 등 편의 피처) |

### 3-2. Step 2~3 (정제·통합)

| 항목 | 설계 목표 | 현재 상태 |
|---|---|---|
| XML → Parquet 정제 (staged) | `year/month/sigungu` 3단 파티션 | ✅ 20,381개 parquet (2006~2026 전체 파티션 채워짐) |
| `apt_id_map.parquet` | 단지명 정규화 + fuzzy 매칭 | ✅ 1.0MB 빌드 완료 |
| `trade_events.parquet` | 거래 이벤트 단위 단일 테이블 | ✅ 70.4MB |
| `unified_apt_pyeong_daily.parquet` | 60컬럼 통합 분석 데이터셋 | ✅ 11.7MB (최근 90일 스냅샷) |

### 3-3. Step 4~8 (콘텐츠 파이프라인 — 설계서 4·5·7장 대응)

| 단계 | 스크립트 | 산출물 | 상태 |
|---|---|---|---|
| Step 4 | `run_step4_unified_daily.py` | unified 일별 빌드 | ✅ 작동 |
| Step 5 | `run_step5_recommend.py` | 지역별 추천 (가중치 적용) | ✅ `exports/daily/recommend_*.parquet` |
| Step 6 | `run_step6_model.py` | 가격 예측 모델 + 백테스트 | ✅ `config/regional_weights.json` 보유 |
| Step 7 | `run_step7_undervalue.py` | 시군구별 저평가 Top 5 | ✅ `undervalue_top5_*.parquet` 일별 생성 (~5/7까지) |
| Step 8 | `run_step8_new_trades.py` | 신규 거래 워터마크 비교 | ✅ `new_trades_*` + `new_trades_sgg_*` |

### 3-4. 자동화 · 운영 (설계서 4·6·7장)

| 항목 | 설계 목표 | 현재 상태 |
|---|---|---|
| 일별 오케스트레이터 | 04:00~06:30 자동 실행 | ✅ `run_daily_update.py` (0~7단계 일괄 실행) |
| GitHub Actions / cron | 무인 실행 | ⚠️ 스크립트는 준비, 스케줄러 등록은 확인 필요 |
| Slack 실패 알림 | P1/P2/P3 3단계 | ❌ 미구축 (`secrets.json`의 `slack_webhook` 빈 값) |
| `quality_check` 8종 sanity | 영상 송출 차단 회로 | ❌ 자동 회로 미구축 |
| `master/` 매일 백업 | 05:30 별도 위치 복제 | ⚠️ 수동 백업 1회 (`master.backup_20260502_163024`) |
| 해제·정정 처리 | `is_canceled` 컬럼 운영 | ✅ Step 4에서 `is_canceled=False` 필터링 |
| 신규 단지 검토 큐 | 월 1회 사람 검수 | ❌ 미구축 |

## 5. 다음에 손대면 좋은 순서

설계서의 위험도 격리 원칙을 따른다면 권장 우선순위는 다음과 같다.

1. **`quality_check` 자동 회로 + Slack 알림** — 이미 일별 잡이 매일 돌고 있어서, 잘못된 산출물이 영상으로 나갈 위험이 가장 큼.
2. **전월세 RTMS 수집** — 설계서 1.2의 전세가율 피처가 빠져있어 Step 2 모델 정확도 천장이 낮은 상태.
3. **인구·학군·상권 정식 SCD Type 2 스냅샷** — 대체 수집은 '현재값'이라 과거 거래 분석에 시점 오염 가능.
4. **신규 단지 월별 검수 큐** — 매월 1~3% 누락이 누적되면 통계가 점점 어긋남.
5. **`master/` 자동 일일 백업** — 한 번의 실수로 1년치 정정 이력이 날아갈 수 있음.
