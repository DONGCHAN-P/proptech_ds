# 집고리즘 통합 웹서비스 방향안 v1

작성: 2026-10-19. 현재 프로젝트의 맞춤 찾기 디자인을 계승한다. 이 문서는 사용자 요구와 실제 Claude CLI 리뷰를 검토한 **Codex의 권장 설계**다. 운영 서비스 완성·외부 배포·회원 연동 완료를 의미하지 않는다.

## 이번에 정리한 범위

사용자는 예산 계산기, 회원 전용 아파트 추천, 공개 단지 정보를 하나의 웹에서 제공하고 로그를 저장하려 한다. 첨부한 `realestate_next_series_master_plan.md`는 하남 이후 시리즈와 서비스 연결의 참고 자료로 읽었다. 그 문서의 영상 수정·투자 분석·일정·배포 지시는 별도로 실행하지 않았다. 문서 속 영상 말투나 옛 브랜드 색상도 현재 확정 지침을 덮어쓰지 않는다.

이번 산출물은 코드 현황 검토, 실제 Claude 리뷰, 서비스 설계, 독립적인 클릭형 디자인 시안이다. 기존 `web/main.py`, `web/match.py`, 운영 데이터·회원·공개 주소는 변경하지 않았다.

## 1. 세 기능을 하나의 집 찾기 흐름으로 연결한다

서비스 이름은 **집고리즘**, 신뢰 근거와 콘텐츠 브랜드는 **데이터로 보는 부동산**으로 연결한다. 첫 방문부터 세 기능 중 원하는 곳으로 진입할 수 있게 하고, 기본 출발 화면은 예산 계산으로 제안한다. 유튜브 링크는 홈을 거치지 않고 해당 계산기·지역·단지 화면으로 연결할 수 있다.

| 기능 | 비회원 | 회원 | 화면에서 얻는 것 |
|---|---|---|---|
| 내집마련 예산 계산 | 입력·계산·결과 확인 | 별도 선택 시 결과 저장 | 권장 예산, 월 원리금, 초기 비용, 남길 비상금 |
| 아파트 추천 | 질문 작성·기능 설명 | 추천 실행·재실행·선택한 결과 저장 | 조건에 맞는 후보, 선정 이유, 아쉬운 점, 비교 지도 |
| 아파트 정보 | 지도·검색·단지·실거래·지하철·학교 | 관심 단지 저장 등 개인 기능 추가 | 가격과 위치·생활시설을 함께 파악 |

```text
유튜브 / 검색 / 직접 방문
  ├─ 예산 계산 (비회원) ─ 이 예산으로 찾기 ─┐
  ├─ 맞춤 질문 작성 (비회원) ───────────────┤
  │                                  로그인·가입
  │                                      ↓
  │                          회원 추천 실행 → 후보 비교
  │                                      ↓
  └─ 공개 지도·단지 정보 ←────────────── 단지 상세
                                        ↓
                               관심 단지·선택 결과 저장
```

추천 실행 직전 로그인하게 하고, 가입 후 입력하던 조건으로 돌아오게 한다. 처음부터 회원가입을 강요하지 않되, 비회원에게 실제 추천을 1회 실행해 주는 정책은 사용자의 명시 조건과 달라 채택하지 않는다. 공개 단지 상세와 가격 이력을 추천 회원 기능으로 다시 잠그지 않는다.

회원가입은 검증된 인증 공급자의 간편 로그인을 우선 검토한다. **Supabase Auth + Postgres**를 우선 후보로 제안하되 공급자 계약·프로젝트 개설·유료 플랜 선택은 아직 하지 않는다. 국내 사용자용 카카오와 구글 로그인을 검토하고, 초기에는 검증·설정 가능한 공급자부터 연동한다. 공급자 로그인 성공과 서비스 가입 완료를 구분해 약관 동의·탈퇴 경로도 만든다. 이메일 외 이름·전화번호·주민번호는 기본 가입에 요구하지 않는다.

## 2. 디자인은 기존 맞춤 찾기의 장점을 계승한다

전면 재디자인으로 채널과 기존 서비스의 익숙함을 버리지 않는다. 현재 `web/static/css/match.css`의 바이올렛 강조, 단계형 질문, 둥근 카드, 차분한 지도를 유지한다.

| 영역 | 디자인 기준 |
|---|---|
| 상단 공통 탐색 | 집고리즘 / 예산 계산 / 맞춤 찾기 / 아파트 지도 / 로그인·내 저장함 |
| 홈·계산 입력 | 따뜻한 흰색·옅은 보라, 명확한 질문, 기본 입력과 추가 조건 분리 |
| 맞춤 질문 | 현재 6단계 경험 계승, 진행도와 고른 조건 유지, 가구 유형으로 학교 조건을 강제하지 않음 |
| 계산·추천 결과 | 불투명 흰 카드, 짙은 본문, 큰 핵심 숫자, 선정 이유·아쉬운 점을 같은 위계로 표시 |
| 지도 | 실거래 가격과 면적을 함께 표시, 실제 노선 색상과 역, 학교 구분, 레이어별 범례 |
| 단지 상세 | 거래 기준·기간·건수 → 가격 추이 → 통근·생활시설 → 비교 순서 |
| 모바일 | 읽기 쉬운 단일 열 입력, 지도는 넓게, 후보·상세는 하단 패널로 연결 |

보라색은 버튼·선택·추천 순위를 나타낸다. 상승·하락 색상과 충돌하지 않게 의미를 분리한다. 메시 그라디언트와 반투명 효과는 질문·배경 일부에만 쓰고 지도·숫자·표에는 적용하지 않는다. 라이트 모드를 먼저 완성하고 동일 토큰으로 다크 모드를 맞춘다. 폰트는 기존 Pretendard 계열을 재사용한다.

클릭형 시안: [web/design/20261019/index.html](../../../web/design/20261019/index.html). 예산·추천 질문·지도 탭, 로그인 안내, 지도 레이어 토글을 눌러볼 수 있다. **화면의 금액·단지·지도는 명시된 샘플이며 실제 금융 계산·추천·인증·수집 기능은 없다.** 기능 검토용이 아니라 디자인과 흐름 검토용이다.

## 3. 예산 계산기는 최대 대출액보다 감당 가능한 매수가를 중심에 둔다

입력은 현금·연소득·기존 부채 상환·남길 비상금으로 시작하고, 대출기간·금리·월 생활비·주택 보유·지역 조건을 추가로 받는다. 실제 규칙에서 요구되는 항목은 빠뜨리지 않는다.

결과에는 아래 항목을 함께 제시한다.

- 보수·기준·상한 시나리오의 매수가와 예상 월 원리금.
- 실제 상환 금액과 대출 심사용 상환 부담을 구분한 설명.
- 취득세·중개보수·등기·이사 등 초기 비용의 항목별 내역.
- 비상금을 제외한 사용 가능 현금과 구매 후 남는 현금.
- 담보·소득·월 현금흐름 중 어떤 조건이 예산을 제한했는지.
- 적용 지역·대상자·시행일·출처·규칙 버전.

LTV·DSR·스트레스 DSR·정책대출·세금 수치를 현재 확인 없이 상수로 만들지 않는다. 정책별 예외는 검증된 것만 지원하며, 지원하지 않는 대상에게 임의의 기본 규칙으로 확정 한도를 제시하지 않는다. 구간별 세율·대출 한도·부대비용 때문에 단순한 `현금+대출` 계산만으로 구매가를 확정할 수 없다. 기존 `content/budget.py`는 실거래의 예산 이하 비율을 계산하는 콘텐츠 모듈이며, 개인 주담대 계산기가 아니다.

계산 핵심과 정책 파일을 UI에서 분리해 같은 입력·정책 버전은 같은 결과를 내게 한다. 규칙과 핵심 계산을 한 모듈로 관리해 브라우저와 서버 구현 간 차이가 생기지 않게 검증한다. 기본은 브라우저 계산을 우선하고, 서버가 필요하면 저장하지 않는 계산 요청으로 처리한다. 소득·현금·대출 입력값은 요청 본문 로깅·오류 추적·세션 리플레이 대상에서 제외한다.

추천으로 넘길 때는 필요한 **매수가 상한과 검색 조건만** 넘기며 소득·자산 원문은 넘기지 않는다. 금융값을 URL이나 UTM에 넣지 않는다. 화면 이동은 메모리로 유지하고 OAuth 외부 리다이렉트가 필요하면 검색 초안만 짧게 보관하는 별도 방식으로 처리한다. 예를 들어 탭 범위 임시 저장에 만료 시간을 두고, 로그인 복귀·취소·만료 때 삭제한다. 브라우저 임시 저장도 민감 데이터가 남는다는 점을 고려해 소득 원문을 넣지 않는다. 예산 결과를 계정에 영구 저장하는 것은 별도 사용자 선택이다.

## 4. 공개 전에 추천 품질의 기본 동작을 고친다

현재 엔진을 버리지는 않되 아래 동작은 서비스 목적과 맞게 수정한다. 이 표는 코드와 문서에서 확인한 현재 상태이며 이번에 실제 엔진을 변경한 것은 아니다.

| 확인한 상태 | 권장 변경 |
|---|---|
| 후보 부족 시 예산을 10% 자동 확대 | 예산 상한을 지킨 결과를 먼저 반환. 0~4곳도 정상 결과. 조건 완화는 확인 후 별도 실행 |
| 예산의 75~100% 소진에 높은 점수 | 같은 생활 조건에서 더 비싼 집이 유리해지지 않게 재검토. 선호 면적은 하드 필터로 다루고 월 부담·예산 여유를 별도로 평가 |
| 통근은 역 좌표 기반 가정, Top5만 외부 경로값으로 교체 | 추정 후보 순위와 경로 조회 정보를 구분. 외부 조회를 순위에 반영하려면 동일한 비교 대상·시점으로 재평가. 불가능하면 순위 근거로 과장하지 않음 |
| 학교 지표는 1km 내 초등학교 수 | 학교 위치·직선거리·확인 가능한 배정 자료를 구분. 개수만으로 학군 품질이나 배정을 단정하지 않음 |
| 최근 거래 가격 기반 필터 | 거래 시점·전용면적·유형·건수와 가격 산출 방식을 명시. 현재 그 가격에 매수 가능하다는 표현 금지 |
| apt_id 세대가 달라 브리지 필요 | 안정적 단지 ID와 좌표 매칭률 검사, 동명 단지 오연결·미매칭 표시, 원천 ID 별도 보존 |

추천은 미래 상승률 순위가 아니라 **내 조건에 대한 적합도**다. 가격·통근·생활 선호의 기여도와 결측값, 실제로 적용한 조건을 보여준다. 가격 경쟁력을 추가할 경우 같은 면적·연식·비교 지역을 통제한 정의와 충분한 표본이 먼저 필요하다. 마스터플랜의 가중치는 초기 가설이며 검증 없이 엔진에 고정하지 않는다.

추천 결과에는 `engine_version`, `data_snapshot_id`, 가격 산식 버전, 가중치, 추정/경로조회 출처, 적용 조건과 완화 여부를 연결한다. 사용자가 저장한 결과는 입력·출력 스냅샷을 함께 보관해 재현할 수 있게 한다. 저장하지 않은 실행은 최소 운영 메타데이터만 남기므로 **모든 실행을 완전히 재현할 수 있다고 주장하지 않는다.**

## 5. 기존 앱을 모듈화하고 운영 DB를 분리한다

```text
웹 화면: 예산 / 질문 / 지도 / 단지 / 저장함
                ↓ 같은 서비스 API
FastAPI
  ├─ 공개: 계산 정책·지도·단지·역·학교
  ├─ 회원: 추천 실행·조건 기반 후보 수·추천 기록·관심 단지
  ├─ 인증: 검증된 로그인 공급자·서버 사용자 확인
  └─ 이벤트: 허용된 행동 이벤트만 수신
       ├─ 분석 조회 → DuckDB + 버전 고정 Parquet
       └─ 운영 기록 → Postgres

기존 수집·정제 배치 → 검증된 데이터 스냅샷 → 공개/추천에 배포
```

당장 React/Next.js로 모두 재작성하거나 기존 분석 데이터를 운영 DB로 전량 옮기지 않는다. 기존 FastAPI·순수 추천 함수·데이터 빌드·지도 자산을 재사용하고, 공개·회원·계산·이벤트 경계를 라우터와 서비스 모듈로 분리한다. 프론트는 먼저 공통 토큰과 작은 UI 모듈을 정리한다. UI 복잡도와 팀 운영상의 필요가 확인될 때 프레임워크 전환을 별도 판단한다.

Postgres에는 계정 최소 프로필, 관심 단지, 선택 저장한 예산 시나리오, 추천 실행 메타데이터, 정책 버전, 제한된 이벤트만 둔다. 지도를 빠르게 탐색할 공간 조회가 필요하면 현 인덱스와 공간 엔진을 측정한 뒤 PostGIS 도입 여부를 정한다. 전국 거래 원장을 무조건 작은 호스팅 DB에 먼저 넣지 않는다.

### 서버에서 지켜야 하는 접근 권한

`POST /api/match`와 개인 조건에 따른 `POST /api/match/count`는 인증 후 처리한다. 비회원 질문 단계에서는 실제 후보 수 대신 단계 안내를 표시할 수 있다. 로그인 UI만 가리고 기존 공개 API가 그대로 남는 구현은 완료가 아니다. 계정 없는 체험용 샘플은 실제 개인 추천 실행과 분리한다.

토큰의 서명·발급자·대상·만료를 서버에서 검증하고 사용자 ID는 요청 본문에서 믿지 않는다. 저장함·계산 결과·추천 기록은 본인 것만 조회·수정·삭제할 수 있게 한다. 브라우저에서 DB에 접근하는 구성이면 RLS와 최소 권한을 적용한다. FastAPI가 관리자 권한 연결로 RLS를 우회하면 API의 소유권 검사가 별도로 필수다. 관리자/service-role 키는 프론트에 노출하지 않는다. 쿠키 기반 세션이면 HTTPS·쿠키 속성·CSRF와 로그아웃 처리를 함께 검증한다.

인증 상태별 제한 외에 공개 데이터와 회원 추천 모두 호출 빈도·시간 제한·캐시·동시 실행 한도를 둔다. 유료 길찾기 API는 별도 예산과 쿼터를 둔다. MVP가 추천 요청마다 LLM을 호출할 필요는 없다. 선정 이유는 검증된 점수와 데이터에서 생성해 비용과 재현성을 관리한다.

## 6. 로그는 세 가지로 나누고 개인정보 저장과 구분한다

| 구분 | 목적·예시 | 저장하지 않을 것 |
|---|---|---|
| 운영 로그 | 요청 ID, 라우트 템플릿, 응답 코드, 처리 시간, 안전한 오류 코드 | 원문 본문·전체 URL/쿼리·금융값·토큰·쿠키 |
| 보안 감사 | 로그인 성공/실패, 권한 차단, 계정 삭제, 관리자 작업 | 비밀번호·세션 값·인증 코드·공급자 토큰 |
| 제품 행동 | 계산 시작/완료, 단계 완료, 로그인 진입, 추천 완료, 단지 저장 | 소득·자산 원문·정밀 직장 좌표·이메일·검색창 원문 |

사용자별로 다시 보고 싶은 정확한 예산이나 추천 조건은 **서비스의 개인 저장 데이터**다. 분석 이벤트의 무제한 JSON에 섞지 않는다. 가명 사용자 ID를 붙인 데이터도 완전 익명이라고 부르지 않는다.

초기 이벤트 예시:

```json
{
  "event_id": "validated-uuid",
  "event_name": "recommendation_completed",
  "server_time": "server-assigned",
  "user_id": "server-authenticated-opaque-id",
  "route": "/match",
  "props": {"result_count": 5, "engine_version": "fit-v2"}
}
```

`props`는 이벤트별 허용 필드·타입·길이로 제한한다. 서버가 사용자 ID와 시각을 붙이며 추천 완료 같은 핵심 결과는 서버가 기록한다. 중복 `event_id`는 한 번만 집계한다. UTM은 승인한 캠페인 코드로 정규화해 기록하고 원문 URL 전체를 남기지 않는다. 비회원 이동 연결은 추적 동의 정책에 맞춘 짧은 수명의 자체 식별자를 검토하며, 브라우저 지문을 만들지 않는다. 입력을 녹화하는 세션 리플레이는 초기 범위에서 제외한다.

운영 30일·제품 행동 90일은 **보존 기간 제안**일 뿐 법정 기준이 아니다. 보안 감사·사용자 저장함·백업은 별도 목적과 기간을 정하고 삭제 작업을 운영한다. 탈퇴 시 로그인 공급자·앱 DB·백업에서 어떤 데이터가 언제 삭제되는지 명시한다. 프록시·호스팅·인증 공급자의 접근 로그는 앱과 별개로 확인한다. 부정 사용 탐지를 위한 IP 처리도 목적과 짧은 보존 방식을 따로 결정하며 '어디에도 IP가 남지 않는다'고 약속하지 않는다.

초기 운영 화면의 지표는 유튜브 캠페인별 유입 → 예산 완료 → 맞춤 질문 완료 → 가입 → 추천 성공 → 단지 저장으로 잡는다. 관리자에게는 집계 중심으로 보여주고, 개인별 소득·자산 목록을 분석 대시보드로 만들지 않는다. 사용자의 목표와 다른 비회원 추천 체험 전환율을 기본 KPI로 쓰지 않는다.

## 7. 데이터는 영상과 웹이 함께 쓰는 한 기준으로 관리한다

SHP를 브라우저로 매번 내려받기보다 원본을 보존하고 좌표계·스키마·출처를 통일한 뒤 용도에 따라 GeoJSON/타일/서빙 인덱스로 변환한다. 웹과 영상의 단지 ID·노선·시설·토지계획 참조를 공유하되 사용자 데이터는 영상용 데이터에 섞지 않는다.

학교·역·노선은 실제 운영 상태와 계획 상태를 구분하고, 학교 거리와 배정은 다른 정보로 제공한다. 가격은 대표 면적·기간·취소 제외 방식·거래건수를 붙인다. 추천 결과는 데이터 스냅샷을 가리키고 공개 지도는 최신 갱신일을 보여준다. 원천별 재배포·상업 이용·캐시 조건과 표시해야 하는 저작권을 확인한다. 기존 개발용 타일·과거 배포 README를 공개 운영의 이용 허가나 현재 비용 확인으로 간주하지 않는다.

## 8. 구현 순서와 완료 기준

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 공통 UI·공개 지도·예산 엔진 | 실제 자료 연동, 반응형 화면, 최신 규칙 근거 및 경계 테스트, 입력 원문 로그 유출 없음 |
| 2 | 인증·추천 보완·저장함 | 비회원 API 직접 실행 차단, 다른 회원 데이터 접근 차단, 예산 자동 완화 없음, 로그인 후 입력 복귀 |
| 3 | 운영 로그·이벤트·관리자 집계 | 허용 이벤트만 저장, 중복 제거, 오류·권한 기록 검증, 보존·삭제 작업과 집계 지표 확인 |
| 4 | 제한된 실제 사용자 베타 | 데이터 갱신·백업 복구·부하·접근권한·동의/탈퇴·지도 라이선스 검증 후 공개 |

로그의 스키마와 민감정보 제외 규칙은 **1단계부터** 적용하고, 관리자 대시보드는 나중에 만든다. 계산과 추천 데이터의 정확도·보안이 준비되지 않은 화면을 '운영 완료'로 게시하지 않는다. 도메인·호스팅·회원 공급자 프로젝트는 실제 운영 상태와 예산을 확인한 뒤 연결한다.

### 다음 구현에서 먼저 확정할 운영 선택

1. 인증·DB·호스팅: 기존 배포가 실제 운영 중인지 확인하고 공급자·지역·요금 한도를 결정한다. 우선안은 현재 FastAPI + 관리형 Auth/Postgres다.
2. 개인정보·로그: 보존·삭제·사용자 저장 범위와 필요한 고지·동의 방식을 정한다.
3. 예산 규칙 지원 범위: 수도권 일반 주담대부터 시작할지, 생애최초·정책대출을 초기부터 지원할지와 검증 담당을 정한다.

이 세 가지는 현재 미확정 운영 선택이다. 기존 화면 디자인을 다시 확인하거나 모든 세부 편집에 승인받는 절차를 만들지는 않는다.

## 9. Claude 검토 결과와 Codex 판단

실제 구독 Claude CLI 1회 리뷰를 수행했다. 원문·실행 receipt는 `analysis/website-direction-v1/`에 보존했다. 도구·MCP 호출은 비활성화했고 자격증명과 원천 사용자 데이터는 프롬프트에 넣지 않았다. CLI에 표시된 비용 추정은 추가 API 청구 증거가 아니다. 외부 유료 생성 API 호출·유료 계정 개설·배포는 하지 않았다.

채택한 의견은 현재 스택 재사용, 운영·분석 DB 분리, 질문형 디자인 계승, 데이터 화면의 가독성 우선, 민감 입력 로깅 제외, 추천 버전 추적이다. 비회원에게 실제 추천을 1회 제공하자는 제안은 사용자 운영 조건과 달라 미채택했다. 예산을 URL에 넣자는 흐름도 채택하지 않았다. 상세 단지 정보를 회원 전용으로 잠그는 안은 무료 정보 제공 요구와 달라 미채택했다. 로그 규칙은 마지막 단계로 미루지 않고 최초부터 적용하는 것으로 보완했다. 따라서 '모든 세부에 양측 합의'가 아닌 **Claude 리뷰를 반영한 최종 권장안**이다.
