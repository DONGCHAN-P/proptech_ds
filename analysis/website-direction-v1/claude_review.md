## 집고리즘 웹서비스 — 동료 리뷰

---

### 1. 동의 / 반대

**동의하는 것**

- 홈을 광고페이지 대신 행동 3개(예산→조건→지도)로 구성하는 방향은 정확하다. 사용자가 채널에서 넘어올 때 이미 "살 수 있나?"라는 질문을 품고 온다.
- 예산 자동 10% 완화 금지. 0결과도 정직한 결과다. 완화는 사용자가 선택해야 한다.
- 운영 DB(Postgres)와 분석 DB(DuckDB/Parquet) 분리. 현재 match.py가 순수함수이므로 경계가 이미 존재한다.
- 정적 UI 잠금만으로 API 보호하지 않는다는 원칙. /api/match가 현재 인증 의존성이 없는 상태이므로 서버 쪽 gate가 반드시 필요하다.

**반대하거나 조건이 필요한 것**

**회원 gate 위치.** Codex 초기안은 "최종 알고리즘 실행 및 결과 저장 시 회원 인증"을 제안한다. 그런데 추천 실행 자체를 회원 전용으로 막으면 채널 이탈자를 서비스로 끌어들이는 힘이 사라진다. 비회원도 추천 결과를 1회 볼 수 있어야 한다. 단, **결과 저장·재열람·상세 리포트**는 회원 전용으로 gate한다. API 남용 방지는 rate-limit + 세션 토큰으로 대응하는 것이 균형이다.

**금융 계산기의 "기본 로그에 남기지 않음" 원칙.** 동의하지만 표현이 느슨하다. 소득·현금·대출액은 **서버에 아예 저장하지 않고 클라이언트에서만 계산**하거나, 서버 계산이 필요하면 요청-응답 즉시 파기하는 stateless 처리임을 구현 규칙으로 명문화해야 한다. "기본 로그에 남기지 않음"은 실수로 error log에 포함될 여지가 있다.

### 2. 3기능 연결 흐름과 회원 gate

```
[유튜브 영상 → CTA 링크]
         ↓
  홈: 예산 확인 / 아파트 찾기 / 지도  ← 공통 header
         ↓
[예산 계산기] — 비회원, 클라이언트 계산
  → '이 예산으로 찾기' 클릭
  → URL: /match?budget=X&area=Y (금융 원본값 제외, 결과 파라미터만)
         ↓
[6단계 질문] — 비회원 작성 가능
  → 제출 → 비회원: 결과 1회 미리보기(Top5 카드만)
  → "저장 / 상세 리포트 / 재탐색"은 로그인 요청  ← gate
  → 로그인 후 원래 결과로 즉시 복귀
         ↓
[지도] — 비회원, 단지·실거래·지하철·학교
  → 지도에서 단지 클릭 → 해당 단지가 내 조건에 맞는지 확인 → 추천 flow 진입
```

gate는 딱 두 곳: **저장·재열람** 그리고 **상세 리포트(통근 실측, 학군 상세, 가격 이력)**. 추천 실행 자체는 비회원 허용, rate-limit 적용.

---

### 3. 현 스택 재사용 vs 전면 재작성

**재사용을 권장한다.** 이유:

- match.py 순수함수, FastAPI 라우터, DuckDB 쿼리는 교체 비용 대비 이득이 없다.
- 전면 React 재작성은 추천 알고리즘 수정·운영 DB 설계·인증 구현이 모두 완료된 뒤 필요성을 판단해야 한다. 지금은 오버엔지니어링이다.
- 현재 index.html이 단일 파일이므로 컴포넌트 분리가 필요해지면 그때 점진 전환.

추가할 것만 추가한다: Postgres(계정/저장/이벤트), Auth managed 서비스(미결 사항으로 남김), 로그 수집 미들웨어. 기존 FastAPI에 router 추가로 충분하다.

### 4. 디자인 구체안

**6단계 질문 화면의 violet/glass 스타일을 계승하되 정보 밀도에 따라 분리한다.**

| 화면 | 스타일 |
|------|--------|
| 홈·질문 | mesh gradient 배경, 반투명 카드, rounded-20, violet accent |
| 추천 결과 카드 | white 불투명, navy text, 그림자만 |
| 지도 | 무채색 base + 컬러 핀(violet/amber/green 의미 구분) |
| 리포트 상세 | white 불투명, 데이터 테이블, 장식 없음 |

다크모드는 지원하되 라이트 우선. Pretendard 유지. 모바일은 지도+bottomsheet, 데스크톱은 지도+사이드 패널. **숫자와 지도에 mesh gradient를 쓰지 않는다.** 장식이 신뢰를 깎는다.

### 5. 로그 스키마 / 실험 지표

**수집하지 않을 것(명문화):** 소득, 현금자산, 대출 원본값, 정밀 직장 좌표, 이메일(행동 이벤트 테이블), raw request body.

**행동 이벤트 테이블 (allowlist):**

```
event_id        uuid
server_ts       timestamptz
route           text          -- /match, /map, /budget
event_name      text          -- step_complete, result_viewed, saved
opaque_user_id  uuid nullable -- 회원만, email 아님
session_bucket  text          -- 중복 방지용 해시, 24h TTL
coarse_utm      text          -- utm_source/medium만
safe_props      jsonb         -- 예산구간(50~60만), 평형구간, 지역코드
```

**운영 오류 로그:** 30일 보존. 개인식별자 제외.  
**행동 이벤트:** 90일 보존(초안). 법적 의무 여부는 별도 검토 필요, 확정 아님.

**핵심 실험 지표 3개:**
1. 예산→질문 전환율 (채널 CTA 효과)
2. 질문 완주율 (6단계 중 이탈 단계)
3. 결과 열람→회원가입 전환율 (gate 위치 검증)

### 6. 추천 알고리즘 공개 전 필수 수정

우선순위 순:

1. **예산 자동 완화 제거.** 이미 합의됨. 구현 확인 필수.
2. **가격 표시 방식 수정.** "최근 거래 1건 = 현재 매수 가능 가격"처럼 읽히는 표현을 "최근 실거래가(날짜 명시), 현재 호가·매수 가능 여부는 확인 필요"로 교체. 사실 발명 금지.
3. **통근 거리 표시.** 역간 직선거리 가정임을 결과 카드에 명시. ODsay 값으로 교체하더라도 Top5 이후 순위 재계산을 하지 않으면 "실측 통근 반영"이라고 표현하지 않는다.
4. **학교 표시.** "1km 내 학교 수"임을 명시. "학군 우수"로 표현 금지.
5. **추천 실행 메타데이터 저장.** engine_version / data_snapshot_date / effective_constraints / weights를 추천 결과와 함께 저장해야 나중에 알고리즘 변경 시 이전 결과와 비교 가능.

미래 상승률은 현재 넣지 않는 것이 맞다. 근거 없는 수치보다 없는 것이 낫다.

### 7. 3단계 구현과 완료 정의

**Phase 1 — 예산 계산기 + 지도 공개 (비회원)**
- 예산 계산기: 클라이언트 계산, 서버 저장 없음
- 지도: 실거래·단지·지하철·학교 API 공개
- 완료 정의: 계산 결과가 서버 로그에 남지 않음을 코드 리뷰로 확인. 지도 API rate-limit 적용.

**Phase 2 — 추천 + 회원 gate**
- 필수 수정 6개 항목 적용 후 추천 실행
- Auth managed 서비스 연동 (vendor 미확정 — 미결 사항 1)
- 운영 Postgres 연동: 계정·저장·추천 메타데이터
- 완료 정의: 비회원 추천 1회 가능, 저장은 로그인 후, /api/match 서버 인증 gate 동작 확인.

**Phase 3 — 행동 로그 + 실험 지표**
- 행동 이벤트 allowlist 구현, 개인식별자 제외 검증
- 보존 기간 정책 확정 (미결 사항 2)
- 완료 정의: safe_props 이외 민감 필드가 이벤트 테이블에 없음을 쿼리로 확인.

---

### 미결 사항 (3개 이하)

1. **인증 vendor 선택:** managed OIDC 서비스 비용·규모·데이터 저장 위치 확인 후 확정.
2. **행동 로그 보존 기간 정책:** 90일 초안은 법적 의무가 아니라 운영 판단이며, 실제 적용 전 별도 검토 필요.
3. **Fly.io 실제 운영 상태:** 현재 배포 상태 미확인. Phase 1 시작 전 인프라 현황 파악 필요.
